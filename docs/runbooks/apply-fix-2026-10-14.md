# Runbook: apply the 2026-10-14 database fix

This closes the security holes found on 2026-10-14 and adds the hub tables to the live database. It takes about 45 minutes.

> **Executed on 2026-10-13 by Claude Code, from the terminal (psql with `ON_ERROR_STOP=1`), not the SQL Editor.**
>
> - **Order:** PR #15 was squash-merged before the fix ran, which step 2 of the compatibility check had shown to be safe.
> - **Backup:** `~/ReLoop-backups/backup-2026-10-13-162145.sql`, 12,429 bytes. It holds 12 tables, with row counts matching the live database: 4 users, 4 identities, 9 categories, 5 listings, 2 shops, 1 submission, 3 profiles.
> - **Fix:** `supabase-fixes/2026-10-14.sql` ran once and committed. Its built-in checks were 13 of 13 true.
> - **Checks:** `supabase-fixes/2026-10-14-checks.sql`, run separately in a read-only session, was 13 of 13 true.
> - **Admins:** 1 account made admin with `make-admin.sql`. The email went through a pipe and was never saved to a file. That account was registered as a shop owner, has not signed in and its email isn't confirmed; the team should confirm it is the intended person.
> - **Live tests (16 of 16 passed)**, against https://re-loop-ochre.vercel.app and the public API with the anon key only:
>   - `/`, `/shop` and an item page return 200 and show the 5 listings;
>   - anon can read listing titles and prices, but gets permission denied on `purchase_cost`, `processing_cost` and `internal_notes`;
>   - anon inserts into `orders` and `enquiries` are refused (401);
>   - a test shop signed up without a GSTIN, stayed `pending`, and the live route refused it (403);
>   - once verified in the database, the route accepted a "Broken" item (200), saved as `Damaged` with "Condition reported: Broken";
>   - a test buyer signed up with role `buyer`.
> - **Cleanup:** both test users were deleted, with their profiles, shop and submission. 0 remain. The table counts are back to the backup's, plus 1 admin.
> - **The connection string** was kept in the macOS Keychain for the run only, and deleted at the end.

Follow the steps in order, and don't skip the checks.

## What you need before you start

1. A Mac with the ReLoop repo, on branch `chore/prod-health`, with these files:
   - `scripts/backup-live-data.sh`
   - `supabase-fixes/2026-10-14.sql`
   - `supabase-fixes/2026-10-14-checks.sql`
   - `supabase-fixes/make-admin.sql`
2. Access to Vercel, from which you open Supabase.
3. The database connection string: the same "Session pooler" one you pasted for the read-only check. In Supabase, click **Connect** at the top, then **Session pooler**, and copy the URI with the password filled in. Never paste it into a chat, a document or git.
4. The email address of the person who will be the ReLoop admin. They must already have registered at `/register` and logged in once.
5. Two email addresses you can use for test accounts, such as `yourname+shop1@gmail.com` and `yourname+shop2@gmail.com`.
6. Nobody else changing the database or merging pull requests while you work.

## Why this order

- The site running today keeps working after the fix, which has been tested query by query. So fixing the database first closes the holes straight away.
- PR #15 adds a "Not GST-registered" option at sign-up. That option only works once the database has been fixed.

So: **back up first, then run the fix script, then check it, then merge PR #15.**

## Part A: Back up

1. Open **Terminal** and go to the repo:
   `cd ~/Desktop/ReLoop/ReLoop`
2. Run the backup:
   `zsh scripts/backup-live-data.sh`
3. When asked, paste the connection string and press Enter. Nothing appears while you paste; that's normal.
4. **Good** looks like `Backup done: /Users/…/ReLoop-backups/backup-<date>.sql (…, 12 tables)`. The size should be at least a few KB.
5. **If it says `Backup FAILED`:** stop here, and don't run the fix. Usually the connection string or the password is wrong; copy it again from Supabase → Connect and retry.
6. Keep the backup file private. It holds customers' personal details and password hashes, so don't email, upload or share it.

## Part B: Run the fix script

7. In Vercel, go to **Storage**, click **supabase-ReLoop-Jammu**, then **Open in Supabase** (top right).
8. Check you are in the right project: its name should match what Vercel shows.
9. In Supabase's left sidebar, click **SQL Editor**, then **+ New query**.
10. Optional but useful, a "before" picture:
    - Open `supabase-fixes/2026-10-14-checks.sql` in VS Code, copy all of it, paste it into the editor, and click **Run**.
    - You should see a table of 13 checks, several with `ok = false`. These are the open holes.
    - This changes nothing.
11. Get the editor ready to change things:
    - If the editor shows a **Read-only** switch, turn it **off**.
    - If it shows a **role** picker, choose **postgres**.
12. Open `supabase-fixes/2026-10-14.sql` in VS Code. Select all (Cmd+A), copy, and paste it into a new query, replacing anything already there.
13. Click **Run**. If Supabase warns that the query has "destructive operations", click **Run this query**. The script removes policies and permissions on purpose; it deletes no data.
14. **Good** looks like "Success. No rows returned", or a table of 13 checks that are all `true`.
15. **Bad** looks like a red error:
    - An error starting `ReLoop fix checks failed, so nothing was changed` lists the checks that failed.
    - Any other red error also means **nothing was changed**: the whole script is one transaction.
    - Copy the full error text and go to [Part F](#part-f-if-something-goes-wrong). Don't edit the script or run it again.
16. If the editor had a Read-only switch, turn it back **on**.

## Part F: If something goes wrong

- **The backup failed:** don't run the fix. Retry the backup with a freshly copied connection string.
- **The fix script showed a red error (step 15):** nothing was changed, and the site works as before. Send your engineer the exact error text. Don't change the script or run parts of it.
- **A check shows `false` after a successful run (step 19):** this shouldn't be possible, because the script refuses to finish if any check fails. Send your engineer a screenshot of the check table.
- **The shop stops loading after the fix but before the merge:** this is very unlikely; it was tested query by query.
  1. In Vercel, go to **Logs** and look at errors on `/shop`.
  2. As a temporary emergency measure that brings the shop back, run:

     ```sql
     grant select on public.listings to anon, authenticated;
     ```

     **This reopens the High security hole** (anyone can read purchase costs and notes), so tell your engineer straight away.
- **Something breaks after merging PR #15:** in Vercel, go to **Deployments**, open the previous production deployment, and click **Instant Rollback**. The database fix stays in place, and the old code works with it.
- **Data was lost or damaged:** nothing in this runbook deletes or edits your data. Of the existing data, the fix script changes only the storage bucket settings. Restoring is a last resort that replaces the live data with the backup, logging everyone out. **Do it with an engineer**, after confirming the backup file is the right one:

  ```sh
  zsh -c 'read -rs "PGURL?Connection string (hidden): "; echo
  F=~/ReLoop-backups/backup-<date>.sql
  TABLES=$(grep "^COPY " "$F" | cut -d" " -f2 | paste -sd, -)
  /opt/homebrew/opt/libpq/bin/psql "$PGURL" --single-transaction -v ON_ERROR_STOP=1 \
    -c "SET session_replication_role = replica" \
    -c "TRUNCATE $TABLES CASCADE" \
    -f "$F"
  unset PGURL'
  ```

  - It empties exactly the tables that are in the backup, then loads the backup, all in one transaction. If anything fails, nothing changes.
  - It has not been tried against the live database.
